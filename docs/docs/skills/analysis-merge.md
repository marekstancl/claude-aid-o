# Analysis Merge

When multiple analysis agents (security, backend, architect, and others) review the same EPIC step, their findings must be consolidated into a single actionable report. This skill defines three merge strategies, the structured output format, and how the orchestrator triggers, collects, and evaluates multi-perspective analysis.

## Purpose

Multi-agent analysis surfaces more issues than any single reviewer, but it also produces duplicate findings, contradictory severities, and noise. The analysis merge skill solves this by providing deterministic algorithms to combine findings in a way appropriate to the review context: capturing everything for security reviews, filtering to confirmed issues for database validations, or weighting expert opinion for architecture reviews.

## When Used

- Triggered automatically after PHASE_CHECK when the EPIC plan defines `analysis_groups` targeting a completed step
- Invoked for security reviews, architecture audits, database migration validation, and pre-release checks
- The `planner` skill auto-generates `analysis_groups` for security-sensitive, high-complexity, or contract-changing steps
- PM can override the auto-selected strategy during PLAN_REVIEW

## Key Concepts

### Three Merge Strategies

**Union** keeps all findings from all agents. Nothing is discarded. The same issue appearing in two agents produces two entries, both tagged with `source_agent`. Best for security reviews and first reviews of new code.

**Consensus** keeps only findings confirmed by two or more agents using similarity scoring: same file path (+0.4), same category (+0.3), same severity (+0.2), keyword overlap (+0.1). A similarity score of 0.6 or above counts as a consensus match. Unmatched findings go to a `minority_findings` section rather than being discarded. Best for reducing false positives in large analysis groups (3+ agents) and pre-release audits.

**Weighted** ranks findings by agent domain expertise. A security agent's security finding scores `3.0 * 1.0 = 3.0`; a frontend agent's security finding scores `3.0 * 0.4 = 1.2`. The expert's finding is kept; the other is listed in `also_reported_by`. Best for architecture reviews and cross-cutting concerns.

### Input Format

Every analysis agent must produce YAML output with `findings[]`, each containing:
- `severity`: critical, high, medium, low, or info
- `category`: security, performance, architecture, correctness, or style
- `location`: file path and optional line number
- `finding`: description of what was found
- `recommendation`: what should be done
- `confidence`: high, medium, or low

Agents that produce invalid YAML are skipped with a warning. Consensus and weighted strategies require at least two valid agent outputs; otherwise they fall back to union.

### Criticality Evaluation

After merging, the orchestrator evaluates the result:
- **Critical findings** trigger immediate escalation; the PM must acknowledge before the pipeline continues
- **High findings** log a warning and notify the PM (non-blocking)
- **Medium, low, info** — the pipeline continues normally

## How It Works

1. The Controller detects `analysis_groups` in the plan targeting the completed step
2. Analysis agents are dispatched in parallel (single message, multiple Task calls)
3. Each agent output is validated against the required YAML structure; invalid outputs are skipped
4. The configured merge algorithm runs on all valid outputs
5. An `analysis_report` is generated with findings, action items, statistics, and improvement notes
6. Raw agent outputs and the merged report are saved to the evidence directory
7. Criticality is evaluated; critical findings escalate, others allow the pipeline to continue

Action items are generated by grouping findings by file or module and assigning each group to the agent role best suited to fix it.

## Configuration

The merge strategy is defined in the plan's `analysis_groups` entry:

```yaml
analysis_groups:
  - target_step: "step_3_backend"
    agents: ["security", "backend", "architect"]
    merge_strategy: "consensus"
    mode: "review"
```

The default strategy when no preference is specified is `union` — the safest choice because nothing is discarded.
