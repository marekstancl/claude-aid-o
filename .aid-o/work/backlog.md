## IMP-154 — verify.sh summary message lost when Python exits non-zero under set -e (E-056-2_3 curator)
- **Status:** pending
- **Priority:** low
- **Effort:** M
- **Source:** curator (E-056-2_3)
- **What:** In `ui-calibration-verify.sh`, the line `VERIFY_FAILURES=$(python3 - <<'PYEOF' ...)` runs a Python block that calls `sys.exit(1)` on failures. Under `set -euo pipefail`, this assignment causes bash to exit immediately when Python exits non-zero — so `PY_EXIT=$?` and the summary line `"ui-calibration-verify: N check(s) failed"` are never printed. The individual per-case failure messages (printed by Python to stderr) do reach the terminal and the exit code is correctly 1, so no silent failure occurs — but the structured summary message is lost.
- **Fix:** Change the assignment to `VERIFY_FAILURES=$(python3 - <<'PYEOF' ...) || PY_EXIT=$?` so bash treats a non-zero exit as handled. Then restructure: initialize `PY_EXIT=0` before the block, use `|| PY_EXIT=$?` to capture the failure, and proceed to the `if [[ $PY_EXIT -ne 0 ]]` branch. This preserves the summary message and remains consistent with `set -e` semantics.

## IMP-232 — Canonical plan-level closure + automatic legacy reconciliation

- **Status:** ready
- **Priority:** high
- **Effort:** L
- **Type:** architecture / lifecycle / bookkeeping-integrity
- **Source:** PM escalation after WAN P062 blocked P065 despite completed merge and substantive review (2026-07-13)
- **Affected surfaces:** `scripts/aid-fsm.sh` (`cmd_init`, `done-advance`, `plan-close`), `scripts/aid-plan-close-check.sh`, `skills/pipeline.md`, queue/active bookkeeping, plan-boundary report producers, new closure schema + migration/reconcile command

### Problem

AID has two independently mutable notions of completion:

1. **Delivery truth:** implementation commits merged to the target branch, gates/tests passed, Auditor/Curator review ran, and blocking findings were resolved or explicitly dispositioned.
2. **Bookkeeping truth:** every `fsm-state.yaml.steps[]` row was flipped to `completed`, report frontmatter has a resolvable/fresh `Head`, and a zero-byte `ca-review-complete` marker exists in the expected EPIC evidence directory.

The pipeline does not update these two truth sets atomically. If execution stops after merge/review but before the manual `plan-close` ceremony, later work is blocked even though there is no product defect. The recovery currently requires a human to inspect and hand-edit historical YAML/report metadata, which is both expensive and capable of falsifying provenance if a SHA is guessed or overwritten incorrectly.

There is also a direct contract contradiction in the current implementation:

- `pipeline.md` defines `plan-close` as **one plan-boundary checkpoint after the last EPIC**.
- `cmd_plan_close` writes `ca-review-complete` only inside the single `evidence_dir` passed for one EPIC.
- `cmd_init` scans **every historical EPIC from every other plan** and blocks when any EPIC has `audit-report.md` but lacks its own local marker.

Therefore a correctly closed final EPIC cannot close its sibling EPICs, and any old incomplete bookkeeping record can block unrelated future plans indefinitely. Absence of a marker is also incorrectly reported as "unreviewed findings" even when review artifacts prove the opposite.

### Confirmed reproduction

WAN P062 was merged to `main` by `8ec27dc` with all three EPICs and substantive Auditor review (`pass_no_blocking_findings`, 11/11 acceptance criteria independently checked, 1723 tests passed, ruff clean). `E-062-3_3` has `ca-review-complete`; `E-062-1_3` and `E-062-2_3` do not. Their FSM files say `state:DONE` while retaining pending step rows; `P062-delivery.md` contains a non-resolving `Head` but a resolving `Head_at_generation`, and `P062-boundary.md` lacks `Head`. Starting P065 is blocked solely by these closure artifacts. This is the same recurring bookkeeping-staleness family previously seen when P061 blocked P062.

### Required design

1. **One canonical closure artifact per plan.** Introduce a structured, schema-validated record such as `.aid-o/work/plan-closures/P062.json`; do not use per-EPIC zero-byte files as the source of truth. Minimum fields: `plan_id`, `status`, `covered_epics[]`, `merge_head`, `reviewed_head`, `reports[]` with hashes/heads, `blocking_findings`, `closed_at`, `generated_by`, and `reconciliations[]`.
2. **Atomic automatic closure.** The successful last-EPIC merge/release path must idempotently synchronize step status, validate plan-boundary reports, update queue/active state, and write the plan closure before announcing the plan complete. Manual `plan-close` remains an explicit retry/diagnostic command, not routine operator ceremony.
3. **Relevant-plan lookup only.** Cross-plan init must check the canonical closure of an explicit dependency or the actual immediately preceding plan required by policy. It must never scan every historical evidence directory and infer an active blocker from arbitrary missing files.
4. **Truthful state vocabulary.** Distinguish `delivery_incomplete`, `review_blocked`, and `closure_incomplete`. Only the first two are product/review blockers. `closure_incomplete` should invoke safe automatic reconciliation and produce an actionable diagnostic if reconciliation cannot prove the repair.
5. **First-class legacy reconcile.** Add a dry-run-by-default command, e.g. `aid-fsm.sh plan-reconcile P062 --from-merge <sha> [--apply]`. It may repair only facts it can prove mechanically and must append an audit event for every mutation. It must be idempotent.
6. **No provenance invention.** Never replace a missing/invalid report SHA with current HEAD merely to make a gate green. Preserve a valid `Head_at_generation`; allow current-HEAD annotation only after mechanically proving the intervening delta is documentation/bookkeeping-only. Otherwise require report regeneration or an explicit PM waiver artifact.
7. **Compatibility window.** During migration, read the new plan-level artifact first. Legacy per-EPIC markers may be accepted only through a deterministic adapter that proves all plan EPICs are covered; stop writing new per-EPIC markers after cutover and provide a removal deadline.

### Acceptance criteria

- [ ] Closing the last EPIC of a three-EPIC fixture writes exactly one plan-level closure covering all three EPIC IDs.
- [ ] Starting a dependent next plan succeeds when the canonical closure says `closed`, even if sibling evidence directories have no legacy marker.
- [ ] An unrelated historical plan with missing markers cannot block a new plan.
- [ ] A direct dependency with a real unresolved blocking finding still blocks initialization with the finding/report named.
- [ ] `state:DONE` with pending steps cannot be newly produced; transition/closure either synchronizes the rows atomically or fails before writing DONE.
- [ ] `plan-reconcile --dry-run` reports the WAN P062-shaped inconsistencies without changing files.
- [ ] `plan-reconcile --apply` repairs mechanically provable step/queue/closure drift, records provenance for every change, and is byte-stable on a second run.
- [ ] A non-resolving report `Head` plus a valid historical `Head_at_generation` is never silently rewritten; code/test delta requires regeneration or waiver.
- [ ] A boundary report with no derivable HEAD remains blocked with a regeneration instruction; the tool never guesses a SHA.
- [ ] Missing cross-model/delivery-profile machinery configured as `observe` is recorded in closure assurance but does not masquerade as a code defect or block when policy says non-blocking.
- [ ] Existing genuinely incomplete plans continue to block when delivery or review evidence is absent.
