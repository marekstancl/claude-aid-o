# Plan: AID Orchestrator v0.2.0

## Context

AID v0.1.0 was published to GitHub (`marekstancl/claude-aid-o`) with core orchestration
(EPIC → plan.json → agent dispatch → gates → PM approval). Several gaps emerged during
initial testing and brainstorming:

1. No brainstorming tooling — users depend on external `superpowers:brainstorming` plugin
2. No structured MCP onboarding — users must manually configure Qdrant/Slack
3. No orchestration logging — PM has no way to review what agents did during an EPIC run
4. Static examples that don't showcase the full workflow (brainstorm → EPIC → run)
5. Parallel agent dispatch has no isolation — agents share working directory, causing conflicts
6. No default permissions — every tool call requires manual confirmation
7. LLM cost estimates irrelevant for subscription users (majority of audience)
8. CLAUDE.md gets overwritten on re-init (destroys user's existing content)
9. No CHANGELOG.md or release workflow documentation

## Goal

Deliver v0.2.0 with integrated brainstorming, Qdrant-based orchestration logging,
MCP server onboarding, git worktree isolation for parallel agents, permission presets,
interactive examples, and repo maintenance improvements.

## Scope

**In scope:**
- `/aid-brainstorm` command + brainstorming skill (new command, new skill)
- Qdrant local as default for orchestration logging + PM report generation
- MCP server onboarding in `/aid-setup` (Qdrant, Slack, auto-detect, custom)
- Git worktrees for parallel agent isolation (default strategy, configurable)
- Permission presets in `/aid-setup` (Safe / Recommended / Advanced)
- Document language configuration in `/aid-setup` (default: EN, configurable)
- Interactive examples (replace static files with brainstorming prompts)
- CLAUDE.md intelligent merge in `/aid-init` (marker-based)
- Remove/condition LLM cost estimates from reports
- Lessons learned storage in Qdrant after EPIC completion
- CHANGELOG.md creation + release workflow in CLAUDE.md
- README updates reflecting all v0.2.0 changes

**Out of scope (v0.3.0+):**
- Cross-EPIC analytics and trend dashboards
- Browser-based evidence viewer
- PM decision history / preference learning
- Error pattern detection from Qdrant
- Session continuity via Qdrant
- EPIC templates library

## Step 1: `/aid-brainstorm` Command

**Detailed design:** [P-20260218-bs01](2026-02-18-aid-brainstorm-command-design.md)

### Files to Create

| File | Type | Purpose |
|------|------|---------|
| `commands/aid-brainstorm.md` | Command | Entry point, full flow definition |
| `skills/brainstorming.md` | Skill | Process rules, EPIC subagent prompt template |

### Flow (9 steps)

```
/aid-brainstorm [topic]

1. CHECK: .aid-o/ exists?
   └─ NO → "Run /aid-setup first"

2. CONTEXT: load project-profile.yaml + list existing plans + EPICs
   └─ Understand tech stack, conventions, what's already in progress

3. UNDERSTAND: ask PM one question at a time
   ├─ What do you want to build/solve? (if no [topic] argument)
   ├─ What problem does this solve?
   ├─ Any constraints? (tech, time, budget)
   └─ How do we know it's done? (success criteria)
   Rules:
   - One question per message
   - Prefer multiple choice when possible (AskUserQuestion tool)
   - Focus on: purpose, constraints, success criteria

4. EXPLORE: propose 2-3 approaches
   ├─ Option A (recommended) + pros/cons
   ├─ Option B + pros/cons
   └─ PM selects or mixes

5. DESIGN: present plan sections incrementally, PM approves each
   ├─ Context + Goal
   ├─ Scope (in/out)
   ├─ Approach (chosen option + rationale)
   ├─ High-Level Steps + Constraints + Risks
   └─ Success Criteria

6. REVIEW: "Is the plan OK, or do you want to change/add something?"
   └─ PM iterates until satisfied

7. SAVE: write to .aid-o/01-plans/P-YYYYMMDD-xxxx-topic.md
   └─ Uses plan.md template, 4-char hash generated

8. NEXT STEP: offer two options
   ├─ A) "Here's a prompt for creating an EPIC in a new window:" [copyable text]
   └─ B) "Or I can launch a subagent to create an EPIC draft automatically?"
         └─ Task tool → .aid-o/02-epics/E-YYYYMMDD-xxxx-topic.md from epic.md template

9. COMMIT: "Want to commit the plan (and EPIC draft if created)?"
   ├─ Yes → git add + commit with conventional message
   └─ No → files remain unstaged
```

### Key Principles (adapted from superpowers:brainstorming, MIT, Jesse Vincent)

- **One question at a time** — don't overwhelm PM
- **Multiple choice preferred** — easier to answer
- **YAGNI ruthlessly** — remove unnecessary features from designs
- **Explore alternatives** — always 2-3 approaches before settling
- **Incremental validation** — present design, get approval before moving on
- **HARD GATE** — no implementation until plan is approved
- PM can skip steps ("skip to design") — flow is not rigid
- **Detail by default** — plan must be detailed enough that implementor needs no
  clarifying questions. Every step specifies: what changes, which files, what logic,
  edge cases. Never write vague steps like "Implement feature X" — always expand.
- **Language** — brainstorming conversation follows PM's language. Output document
  (plan file) uses the configured project language (default: EN, set in `/aid-setup`).

### Output

Plan document in `.aid-o/01-plans/P-YYYYMMDD-xxxx-topic.md` following `plan.md` template
with correct AID naming convention (same as sessions and EPICs, including 4-char hash).
Document language follows project configuration (`.aid-o/03-config/policies/`).

## Step 2: MCP Server Onboarding in `/aid-setup`

### What Changes

Update `commands/aid-setup.md` to add a new step after project analysis.

### Flow

```
/aid-setup (new step after tech stack detection)

"AID-O recommends these MCP servers:"

✅ Qdrant Memory (local — no Docker needed)
   Semantic search, lessons learned, orchestration logging.
   Runs in-process via --qdrant-local-path. No server required.
   → Automatically enable? [Yes / No]

   If Yes: claude mcp add qdrant-memory \
     -- uvx mcp-server-qdrant \
     --collection-name aid-memory \
     --qdrant-local-path .aid-o/04-engine/memory/qdrant

   Alternative modes (shown if user says No or wants to change later):
   - Docker: QDRANT_URL=http://localhost:6333
   - Cloud: QDRANT_URL=https://xxx.qdrant.io + API key

⚙️  Slack Notifications (optional)
   PM notifications via Slack. Requires Slack workspace + API token.
   → Want to set up? [Yes / No / Later]

   If Yes: guide through token creation + claude mcp add

🔍 Detected MCP opportunities (based on tech stack scan):
   Example: "Found PostgreSQL in your stack. Want to add MCP server for direct DB access?"
   - PostgreSQL → mcp-server-postgres
   - GitHub Actions → GitHub MCP
   - Supabase → Supabase MCP
   - Docker → Docker MCP
   → Each detected MCP: [Yes / No] (NEVER auto-add without user confirmation)

➕ Custom MCP server
   → Want to add your own? [Yes → instructions for claude mcp add / No]

🌐 Document Language
   "What language for generated documents (plans, EPICs, reports)?"
   → [English (default) / Czech / German / Spanish / Other]
   Stored in .aid-o/03-config/policies/language.yaml: { language: en }
   Note: Brainstorming conversation follows PM's language regardless of this setting.
   Agent-generated code comments and variable names are always in English.
```

### Permissions per MCP

| MCP | Default Permission | Rationale |
|-----|-------------------|-----------|
| Qdrant | `mcp__qdrant-memory__*` (full) | Local data, no external risk |
| Slack | `mcp__slack__*` (full) | User explicitly opted in |
| Detected third-party | Ask user per MCP | Unknown scope, safer to ask |

### Qdrant Local Details

- Uses `--qdrant-local-path` flag — Qdrant runs inside MCP server process
- Data stored on disk at `.aid-o/04-engine/memory/qdrant/` (RocksDB)
- **Persistent** — data survives process restart (not in-memory)
- No Docker, no server, no cloud account needed
- Latency: ~50-200ms per write (vs ~1ms for file write) — negligible for EPIC orchestration
- RAM: ~100MB for small collections

## Step 3: Orchestration Logging + PM Report

### Problem

Controller currently logs state machine transitions to `stage_log.jsonl` but not agent-level
details (which agent got which prompt, what they returned, how long it took, how many retries).
PM has no easy way to review what happened during an EPIC run.

### Solution

**Qdrant local as primary data store** for orchestration data.
`stage_log.jsonl` remains unchanged (lightweight state machine audit log).

### What Controller Logs to Qdrant

For each agent dispatch:
```json
{
  "event": "agent_dispatch",
  "epic_id": "E-20260218-bm01",
  "run_id": "R001",
  "step_id": "step-2",
  "agent": "backend",
  "prompt_file": "prompts/step-2-backend.md",
  "started_at": "2026-02-18T14:23:00Z"
}
```

For each agent completion:
```json
{
  "event": "agent_complete",
  "epic_id": "E-20260218-bm01",
  "step_id": "step-2",
  "agent": "backend",
  "output_file": "steps/step-2-backend/output.md",
  "duration_seconds": 145,
  "retries": 0,
  "status": "success",
  "files_changed": ["backend/app/api/bookmarks.py", "backend/app/models.py"],
  "completed_at": "2026-02-18T14:25:25Z"
}
```

For gate results, retries, escalations — similar structured entries.

### Final Report Generation

At EPIC completion (DONE state), Controller queries Qdrant and generates enriched
`final_report.md` with:

- Summary: total duration, steps completed, gates passed
- Per-agent table: agent name, step, duration, retries, status, files changed
- Gate results with retry history
- Timeline view (which agent ran when, what overlapped)
- Escalation log (if any)

### Graceful Degradation (no Qdrant)

If Qdrant is not configured, Controller generates a basic report from existing evidence
files (`steps/`, `prompts/`, `gates/`, `stage_log.jsonl`). Less detail, but functional.

## Step 4: Git Worktrees for Parallel Agent Isolation

### Problem

When Controller dispatches agents in parallel (e.g., backend + frontend), both agents
work in the same directory. This causes file conflicts and unpredictable behavior.

### Solution

Three isolation strategies, user chooses in `/aid-setup`, can override per EPIC.

### Strategies

**Worktrees (default):**
```
project/                              ← main working directory
.worktrees/
  aid-epic-bm01-backend/             ← full working directory for backend agent
  aid-epic-bm01-frontend/            ← full working directory for frontend agent
```
- `git worktree add .worktrees/aid-epic-bm01-backend -b aid/epic-bm01/backend`
- Each agent gets isolated directory, full project copy (git objects shared)
- After completion: merge branches into main + `git worktree remove` cleanup
- **True parallel isolation** — agents cannot interfere with each other

**Branches (alternative):**
```
main
 ├─ aid/epic-bm01/backend     ← backend agent branch
 └─ aid/epic-bm01/frontend    ← frontend agent branch
```
- Agents share working directory — must stash/checkout between dispatches
- Simpler but **not truly parallel** (sequential checkout switching)
- Merge after completion

**Sequential (fallback):**
- Agents in "parallel" group run one after another on same branch
- No isolation needed, no merge
- Simplest but slowest (loses parallelization benefit)

### Configuration

Stored in `.aid-o/03-config/policies/dispatch-strategy.yaml`:
```yaml
parallel_isolation: worktrees  # worktrees | branches | sequential
worktree_base_dir: .worktrees  # relative to project root
cleanup_after_merge: true       # remove worktrees after successful merge
```

Set during `/aid-setup`. Message displayed:
> "Parallel agent isolation set to **worktrees** (recommended).
> Change anytime in `.aid-o/03-config/policies/dispatch-strategy.yaml`
> or re-run `/aid-setup`."

### Per-EPIC Override

Before `/run-epic`, Controller checks config but user can override:
> "This EPIC has parallel steps (backend + frontend). Using **worktrees** for isolation.
> Want to change? [Use worktrees / Use branches / Run sequentially]"

## Step 5: Permission Presets in `/aid-setup`

### Problem

Claude Code requires confirmation for every tool call. During orchestration with dozens
of agent dispatches, this is very disruptive.

### Solution

Three permission levels configured in `.claude/settings.json` during `/aid-setup`.

### Permission Levels

**Safe:**
- Allowed without confirmation: Read, Glob, Grep (file reading only)
- Everything else requires confirmation
- For users who want full control

**Recommended (default for AID-O):**
- Everything in Safe +
- Edit, Write files — without confirmation
- Bash: test commands, lint, build — without confirmation
- Git: add, commit — without confirmation
- MCP Qdrant: all operations — without confirmation
- **Still requires confirmation:** git push, destructive bash commands (rm -rf, etc.), MCP Slack send_message

**Advanced:**
- Everything in Recommended +
- Git push — without confirmation
- MCP full access (including Slack send) — without confirmation
- **Still requires confirmation:** force push, branch delete, `rm -rf`

### Configuration

Written to `.claude/settings.json`:
```json
{
  "permissions": {
    "allow": [
      "Read", "Glob", "Grep", "Edit", "Write",
      "Bash(test *)", "Bash(npm run *)", "Bash(python -m pytest *)",
      "Bash(git add *)", "Bash(git commit *)", "Bash(git status)",
      "Bash(git diff *)", "Bash(git log *)",
      "mcp__qdrant-memory__*"
    ],
    "deny": []
  }
}
```
(Above example: Recommended level)

### Post-Setup Message

> "Permissions set to **Recommended**. This allows file editing, tests, git add/commit,
> and Qdrant access without confirmation. Git push and destructive commands still require
> your approval. Change in `.claude/settings.json` or re-run `/aid-setup`."

## Step 7: CLAUDE.md Intelligent Merge

### Problem

`/aid-init` currently overwrites CLAUDE.md if it exists, destroying user's project-specific
instructions.

### Solution

Marker-based intelligent merge.

### Logic

```
1. CLAUDE.md exists?
   ├─ NO → Create fresh CLAUDE.md with AID section
   └─ YES → Check for AID markers
              ├─ Markers found (<!-- AID-O START --> ... <!-- AID-O END -->)
              │   └─ Replace content between markers with updated AID section
              └─ No markers found
                  └─ Append AID section (with markers) at end of file
```

### Marker Format

```markdown
<!-- AID-O START — Do not edit this section manually. Updated by /aid-init. -->
## AID Orchestrator

[AID-generated content: project profile, conventions, agent instructions...]

<!-- AID-O END -->
```

### What Changes

Update `commands/aid-init.md` to implement marker detection + merge logic.

## Step 9: Lessons Learned in Qdrant

### Problem

After each EPIC, valuable lessons are lost. What worked, what failed, which gates
needed retries — this knowledge could help future EPICs.

### Solution

At EPIC completion (DONE state), after final report, store structured lessons in Qdrant.

### What Gets Stored

```json
{
  "type": "lesson",
  "epic_id": "E-20260218-bm01",
  "category": "gate_failure",
  "summary": "tests_pass gate failed 2x due to missing test fixtures",
  "detail": "Backend agent didn't create test fixtures for bookmark CRUD. QA agent had to retry.",
  "resolution": "Added fixture creation to backend playbook checklist.",
  "tags": ["testing", "backend", "fixtures"]
}
```

### How Agents Use Lessons

Before agent dispatch, Controller queries Qdrant:
> "Any lessons relevant to [backend] agent working on [API endpoints]?"

Relevant lessons are included in agent prompt as context.

### Graceful Degradation

Without Qdrant: lessons written to `.aid-o/04-engine/memory/lessons-learned.md` (existing
file-based fallback, already implemented).

## Risks

| Risk | Probability | Impact | Mitigation |
|------|-------------|--------|------------|
| `mcp-server-qdrant` local mode instability | low | medium | Fallback to evidence-file-based report. JSONL audit log unchanged. |
| MCP auto-detection false positives | medium | low | Always ask user before adding detected MCPs. Never auto-add. |
| Brainstorming flow too rigid | low | medium | Allow PM to skip steps. "One question at a time" but PM can say "skip to design". |
| Worktree merge conflicts | medium | medium | Controller runs merge, presents conflicts to PM for resolution. |
| Large scope for one release | medium | medium | Steps are independent — can ship incrementally per priority. |
| Permission presets too permissive | low | high | Recommended (not Advanced) as default. Clear messaging about what's allowed. |
